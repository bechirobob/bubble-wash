# Bounded private owner execution

The manual, main-only `Private Personal Owner Enrollment` workflow is separate from code deployment and private diagnostic preflight. Publishing it does not authorize sending anything. It defaults to `mode=check` and `delivery_approved=false`.

Prerequisites: reviewed owner-capable code actually deployed; exact current release SHA; unchanged reviewed owner source and runtime dependency pins; protected existing `backup-storage` recipient secret `BUBBLEWASH_OWNER_EMAIL`; existing tailnet/private-backup checks; existing deployment lock; no duplicate configured/master/managed/roster identity; production SQLite, demo disabled, staff enabled, existing valid personal-MFA encryption key configured; global master/staff MFA flags remain unchanged; no legacy import pending. Missing conditions stop, never invoke recovery/reset.

Inputs contain only the expected deployed SHA, check/send choice, and explicit delivery approval attestation. The recipient never appears in inputs or arguments. Audit inviter is derived from the authenticated GitHub actor, prefixed `github-actions:`. The new managed account's fixed display label is `Personal Owner`; subsequent actions carry that account's own email. This does not impersonate the existing master.

Before `send`, obtain the user's precise per-action approval to transmit the single-use account activation secret through existing Resend to the protected recipient, explaining mailbox/provider exposure could allow account takeover before activation. The separate approval to add an owner does not substitute for delivery approval. Only then dispatch `mode=send` with `delivery_approved=true`. The attestation is an operator guard, not cryptographic proof of the user's consent. No automatic dispatch or reusable consent inference is introduced. Dedicated credential creation and protected-secret installation require separate approval; this workflow does neither.

The fixed proposed sender is exactly `Bubble Wash <bubblewash@becoreops.com>`. This code policy is not sender approval or evidence of provider/domain readiness. The protected environment secret `BUBBLEWASH_OWNER_RESEND_KEY` must be separately authorized and configured. It is streamed privately and used only by the enrollment child process, never written into shared application configuration. Shared `RESEND_API_KEY` and `BUBBLEWASH_EMAIL_FROM` are excluded from that child environment; they cannot substitute for the dedicated secret and do not select or block this sender. Independently verify the intended provider account/domain and obtain exact sender and delivery approval before sending. A verified recent encrypted backup/receipt is required. The host captures bounded env text under the deployment lock, checks it is unchanged after preflight and immediately before spawn, and parses that same snapshot without shell evaluation, forwards only allowed existing app configuration in process memory, strips NODE_OPTIONS/preloads, verifies release/source pins again while holding the existing deployment lock, then runs the reviewed Node enrollment script once as ubuntu. It does not write an env file, token file, script file, or public artifact.

Check mode does not import account stores or create an account/token. Read-only SQLite may touch shared-memory bookkeeping. Send is the only mode allowing insert-only account/capability/audit creation and outbound activation mail. Existing masters/staff, MFA, recovery boundaries and GPS identity restrictions remain unchanged. Recipient collision is rechecked transactionally by the application.

Only fixed categorical results are printed. Child stdout/stderr and provider response bodies are never forwarded. Provider acceptance does not mean delivery or activation. On timeout, rejected/ambiguous delivery, unexpected output, or command interruption, stop and inspect private account/delivery state. Never rerun send, reset, replace, reassign, or reissue automatically. The workflow intentionally has no recovery/retry mode. Later password and personal MFA enrollment happen in the user-facing secure application, not chat.

The existing shared deployment lock is opened through a checked directory descriptor without following links or creating files. Missing, symlink, FIFO, multiply linked, unsafe-owner/mode, and replaced lock identities fail closed. The same helper protects preserving deployment, owner deployment, and enrollment. Its identity is rechecked immediately before the child and before any success report. No lock permissions or host ownership are changed.

## Rollback boundary

The owner-code deployment's automatic rollback is limited to the period before any personal owner is enrolled. Deployment requires the owner capability table to be absent and holds the same exclusive lock used by this enrollment workflow, so approved enrollment cannot overlap activation or its failure rollback.

After personal owner enrollment, never restore pre-owner authentication code: that code can treat the personal owner as an ordinary administrator and drop mandatory personal MFA enforcement, especially when the global MFA setting is false. Any later recovery must retain the owner-aware security code or use a separately reviewed compatible release. Do not delete, downgrade, reset, or replace the personal owner or other accounts to make an old release acceptable. Stop and obtain a separate compatible recovery review instead.

The reviewed first-release `scripts/restore-staff-access.py`, `tests/test_staff_restore.py`, `.github/workflows/restore-staff-access.yml`, and `.github/workflows/staff-access-checks.yml` are retained byte-for-byte in this owner release. They remain a separate, manual emergency staff-login gate restoration route, not part of owner code deployment or enrollment. This assembly does not dispatch that route or authorize environment changes. Any separately authorized use must preserve unavailable customer bookings and the deployed owner-aware authentication/MFA code; it is not a substitute for owner enrollment, a code rollback, or account reset/deletion.
