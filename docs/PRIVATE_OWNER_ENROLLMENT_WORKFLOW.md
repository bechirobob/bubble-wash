# Bounded private owner execution

The manual, main-only `Private Personal Owner Enrollment` workflow is separate from code deployment and private diagnostic preflight. Publishing it does not authorize sending anything. It defaults to `mode=check` and `delivery_approved=false`.

Prerequisites: reviewed owner-capable code actually deployed; exact current release SHA; unchanged reviewed owner source and runtime dependency pins; protected existing `backup-storage` recipient secret `BUBBLEWASH_OWNER_EMAIL`; existing tailnet/private-backup checks; existing deployment lock; no duplicate configured/master/managed/roster identity; production SQLite, demo disabled, staff enabled, required MFA configured; no legacy import pending. Missing conditions stop, never invoke recovery/reset.

Inputs contain only the expected deployed SHA, check/send choice, and explicit delivery approval attestation. The recipient never appears in inputs or arguments. Audit inviter is derived from the authenticated GitHub actor, prefixed `github-actions:`. The new managed account's fixed display label is `Personal Owner`; subsequent actions carry that account's own email. This does not impersonate the existing master.

Before `send`, obtain the user's precise per-action approval to transmit the single-use account activation secret through existing Resend to the protected recipient, explaining mailbox/provider exposure could allow account takeover before activation. The separate approval to add an owner does not substitute for delivery approval. Only then dispatch `mode=send` with `delivery_approved=true`. The attestation is an operator guard, not cryptographic proof of the user's consent. No automatic dispatch, reusable consent inference, new provider credential or host trust is introduced.

The bounded sender is existing `updates@bubblewash.co` (with optional `Bubble Wash` display name). Another configured sender blocks send and requires private review rather than public disclosure. A verified recent encrypted backup/receipt is required. The host captures bounded env text under the deployment lock, checks it is unchanged after preflight and immediately before spawn, and parses that same snapshot without shell evaluation, forwards only allowed existing app configuration in process memory, strips NODE_OPTIONS/preloads, verifies release/source pins again while holding the existing deployment lock, then runs the reviewed Node enrollment script once as ubuntu. It does not write an env file, token file, script file, or public artifact.

Check mode does not import account stores or create an account/token. Read-only SQLite may touch shared-memory bookkeeping. Send is the only mode allowing insert-only account/capability/audit creation and outbound activation mail. Existing masters/staff, MFA, recovery boundaries and GPS identity restrictions remain unchanged. Recipient collision is rechecked transactionally by the application.

Only fixed categorical results are printed. Child stdout/stderr and provider response bodies are never forwarded. Provider acceptance does not mean delivery or activation. On timeout, rejected/ambiguous delivery, unexpected output, or command interruption, stop and inspect private account/delivery state. Never rerun send, reset, replace, reassign, or reissue automatically. The workflow intentionally has no recovery/retry mode. Later password and personal MFA enrollment happen in the user-facing secure application, not chat.
