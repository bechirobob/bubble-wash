# Private owner preflight (inspection only)

This optional mode extends the existing main-only Read-only Release Preflight. It does not enroll an account, send mail, create tokens, provision credentials, or import app modules. Ordinary push runs do not use the recipient secret.

After independent review and merge, an authorized operator must place the approved recipient email in protected environment `backup-storage`, secret `BUBBLEWASH_OWNER_EMAIL`. Do not put it in workflow inputs, public source, commands, artifacts, or logs. Run the workflow manually on main with `inspect_owner=true` and the verified full current deployed SHA in `expected_live_sha`. The existing tailnet and private backup-destination identity checks remain mandatory. Never bypass a denial or failed pin.

The runner streams reviewed source plus safely quoted recipient data through the existing encrypted SSH standard input. No temporary payload file or remote script is written. The host parses the production env without evaluating or sourcing it, verifies the release marker against the expected SHA and current path, then repeats the pin check after inspection.

Output contains only configured/master/managed/roster duplicate categories, sanitized role/status, existing Resend credential presence, and known public sender category. `updates@bubblewash.co` is identified exactly; a different official-domain sender is reported as `other-official-domain`, not exposed. These values describe only shared application transport, not the private owner transport. They neither authorize nor supply the dedicated owner key or fixed proposed sender. The owner-enrollment check reports its private transport separately. Provider presence does not prove a valid credential, domain verification, mailbox delivery, or permission to send an activation link. No new provider credential is provisioned.

The ordinary aggregate database inspection retains its original bounded in-memory byte snapshot and WAL refusal. Private owner inspection separately opens the existing database with SQLite `mode=ro`, `query_only=ON`, `trusted_schema=OFF`, and a read transaction, so committed WAL data is included. It never uses `immutable=1`, imports application stores, creates tables, changes credentials or account data, or copies private database files. SQLite may create or maintain shared-memory (`-shm`) bookkeeping; this is not a promise of byte-unchanged host files. Missing/unsupported schema, views/triggers, read/lock failures, or release drift fail closed. A refused inspection means duplicates are UNKNOWN, never available. It is a point-in-time read transaction; enrollment must recheck collisions inside its insertion transaction.

MFA output validates canonical 32-byte base64 format without printing key material or creating a key. The deployed enrollment command must still use its shared application parser and guards. Main-only source, exact live SHA, unchanged databases and no email are mandatory boundaries; this workflow deliberately contains no send/enrollment mode. Actual enrollment needs the independently reviewed owner-capable deployment plus separate precise activation-delivery authorization.

Missing required account/override/submission tables are reported as fixed table-presence booleans and block collision clearance. The inspection does not initialize tables, import application stores, or infer that an absent table means the recipient is available. Staff roster collisions inspect both the actual `staffEmail` field and legacy `email`, alongside vendor/driver email fields, normalized for case and surrounding spaces.
